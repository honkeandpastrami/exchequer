## Decisions made while building

| Step | Decision |
|---|---|
| 3 | Archived accounts with no transaction in the migrated year aren't migrated: their opening balance would be the only thing in them. The plan report lists them with their balance at the start; the acceptance check compares only the accounts migrated. Accounts in use are always migrated, active that year or not. |
| 8.5 | The editor keeps the server as the judge of ledger rules: it previews a split's kind only to decide which fields to show, and shows the server's message when a save is refused. A month that is closed is reported on save rather than checked beforehand. |
| 8.4 | Charts are drawn by hand in SVG rather than with a chart library: the few shapes needed (lines, columns, bars) are small, the colors stay CSS tokens (a canvas library can't read them), and amounts never pass through floats except as pixel positions. |
| R | One version for the whole repo instead of per-component tags (design §15 updated): the pieces share one spec and move together. Like `firefly-preimporter`, the version is never written in the repo: tags are the only source. The server runs the newest release through `podman auto-update`, so a commit on `main` reaches it only once tagged. |
| 8.2 | With hash routing SvelteKit leaves the query inside `url.hash`, so pages read it through `src/lib/query.ts`. |
| 8.1 | The web app comes before the import pipeline: it's needed to see what's in the database. Sign-in is a pasted API token until Entra (step 9). |
| 8.1 | Hash routing and relative paths keep the proxy prefix out of the build. SvelteKit still writes root-relative paths into the shell `index.html`, so the build rewrites them (`web/scripts/relative-paths.js`, which fails if any remain). |
| 8.1 | Operation IDs were duplicated across resources (`list`, `get`…), which OpenAPI forbids and which made the TS generator merge them. Each is now prefixed with its tag, with a test that they're unique. |
| 8.1 | `openapi-typescript` declares a TypeScript 5 peer while SvelteKit 3 brings TypeScript 6, so it isn't a dependency: `npm run gen` runs a pinned version through `npx`, like the Python SDK generator through `uvx`. |
| 4.5b | Past settlements are corrected only by carrying forward (design §4.4): payments are never rewritten, a fix to a closed month changes its `due`, and the difference stays in `carried` until any later payment pays it down. |
| 4.4 | Balance-check amounts are entered as the bank shows them: on credit cards and mortgages the amount owed is positive. They're stored in the ledger's sign. |
| 4.4 | A check's result is never stored: it's recomputed against the ledger on every read, and `verified_through` is the latest matching check up to its date. Checks are immutable (delete and re-enter); their ETag is fixed. |
| 5.3 | An OFX row's date was the posted date in the file's own time zone; replaced by the server's local date (5.3b). Exact duplicates don't depend on it (OFX rows always have a FITID), and near-duplicate matching allows a few days. Fingerprints follow the preimporter's exactly, so step 5.6 can attach Firefly's `external_id`s to migrated transactions and re-imported rows match them. A CSV line with an unreadable date or amount is reported in `skipped` (line number and reason only), not dropped silently as the preimporter did. OFX files are still read as strict UTF-8, as in step 0.3. |
| 5.1 | Batch IDs aren't time-ordered (backfilled migration batches have random IDs), so batches are listed by creation time and the cursor is the last batch's ID. Undoing a batch takes the batch's ETag rather than none: it deletes many transactions, so it must act on what was seen. Live data keeps one migration batch: regrouping it by Firefly import tag would mean changing `import_batch_id`, which nothing may do. |
| 4.4 | Import coverage gaps (§7.1) wait for import batches (step 5). The candidates are ranked by kind of reason, in the order listed above, at most 25. |
| 4.3 | Grouping and bucketing run in Rust over splits classified by `domain`, not in SQL: kinds and default purposes have one implementation. SQL only selects splits by date and account and sums opening balances. §7 allows it: no materialized summaries until profiling asks. |
| 4.3 | `/query` is a POST although it only reads: the filters are lists. Rows are always per commodity (nothing is valued until step 7); a grouped field is `null` for "none" and absent when not grouped. Tags multiply: a transaction with two tags counts in both. |
